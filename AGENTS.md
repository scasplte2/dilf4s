# Repository conventions

- Keep language implementations and bindings under `lang/<language>`, with their language-specific build files and tests. Scala's sbt build owns Java compilation, with Java sources and build outputs under `lang/java`.
- Keep Lean and its build under `formal`, shared protocol assets under `shared`, and cross-language executables under `tools`. Root configuration must serve the repository as a whole.
- Scala, Rust, TypeScript and Go implement protocol behavior independently. Java binds Scala; Python binds Rust. Coverage gaps belong in `docs/guides/parity.md`, not in an implicit weaker definition of an implementation.
- Use exact corpus counts or exact case-name sets, and assert every expected value and refusal. Never weaken coverage assertions to minimum counts to avoid rebase conflicts. Explicitly account for cases a specialized harness cannot execute, with their expected refusal and an exact excluded set/count.
- Preserve checks that generated sources and shared vectors equal their generators exactly. Moving a generator requires updating its output paths, fixtures and regeneration commands together.
- Use `tools/sbt` from the repository root or `sbt` inside `lang/scala`. Native Rust commands run in `lang/rust/native`; the patched guest has a separate workspace at `lang/rust`. Keep native and SP1 dependency graphs separate.
- A guest-path change can change its ELF and verifying key. Run the SP1 key and proof checks; never loosen or remove the pinned-key assertion to make a layout change pass.
- Keep investigation notes and handoffs in ignored `.workspace/`, never in tracked source or references from tracked documentation.
- Represent failures and internal control states with ADTs. Never use strings as error values or branch on rendered error messages. Keep diagnostics at presentation boundaries, preserve typed causes, and use exhaustive matches over typed discriminants. Apply this to production code, bindings, generators and test tooling.
- This is a hard architectural constraint, not a style preference. Model internal operations, modes, states, variants, roles and refusal reasons with meaningful enums, sealed traits or other closed sum types. Do not dispatch on raw string labels, rendered type names, diagnostic text, prefixes, substrings or string sentinels. Parse external names into typed values at the boundary, then carry those types through the implementation.
- Errors must carry distinct typed cases, structured payloads and original typed causes. `Either[String, A]`, string-valued failure channels and message-only domain exceptions are forbidden. `Error(message: String)`, `Reason(text: String)` and equivalent wrappers do not satisfy this rule. Preserve foreign exceptions as causes rather than replacing them with `getMessage` or `toString`.
- Strings remain valid input data and presentation output; they must not substitute for a domain type or determine behavior through their diagnostic rendering. Render errors only at logging, UI or wire boundaries. Never render an error and parse or inspect that rendering to recover its meaning.
- Apply these constraints equally to generated code and its generators, build tooling, fixtures, benchmarks, tests and adapters. Existing violations are migration work, never precedent for adding another. Do not resolve type/dependency difficulties by converting a cause or control state to a string; fix the type ownership or introduce a meaningful typed boundary.
- Before completing a change, review its error producers, propagation, consumers and adapters for string erasure or dispatch. Tests must assert exact error cases and payloads, including retained causes; diagnostic-text tests verify presentation only and cannot substitute for typed behavioral assertions. Exhaustive matches over closed types must remain compiler-checked.
- Carry authorized work through implementation, review, validation, CI, PR status and cleanup. A completed subtask or an audit is not a stopping point while actionable work remains in the user's requested scope. Stop for a genuinely blocking decision or access requirement, and state the specific blocker.
- Once a PR's scoped changes are complete, review findings are resolved and required checks pass for its current head, convert it from draft to ready without asking again. Verify the resulting GitHub status. Unrelated follow-up work must not keep a completed PR in draft; new commits require checks of the new head.
- Report completed actions only after verifying their results. Distinguish pending checks and remaining work explicitly; do not imply background work will continue after the turn ends.
